## 一、30 秒讲清整条链路（背下来）

```
E53_IS1 传感器 → Hi3861(OpenHarmony 轻量系统) → 串口 JSON(115200, 1 帧/秒)
   → 网关 SerialIngest → telemetry.py 适配成标准快照 → 判定引擎(三档+融合规则)
   → 告警入库(SQLite) → 电脑声光播报 + Web 看板 → 鸿蒙 APP 轮询展示/处置
```

一句话版本：**板子只负责“感知 + 本地声光兜底 + 串口上报”，判定和展示都在网关与 APP。**
（这样改阈值不用重新烧板子，答辩时这也是“为什么这么分层”的答案。）

## 五、四个真机制（讲清这四条，比背功能列表有说服力）

### 1. 任务模型：一个线程 + 两个周期
`SYS_RUN(ElderlyCareAppEntry)`（`main.c:165`）是 OpenHarmony 的启动入口宏，系统初始化完自动调用；
里面 `osThreadNew(ElderlyCareTask, NULL, &attr)`（`main.c:158`）建任务：**栈 8KB、优先级 `osPriorityNormal`**。
主循环 `while(1)`（`main.c:56`）里：
- **50ms 节拍**：`EmergencySosPoll()` 扫按键 + `AlarmBeeperTick(50)` 推进声光状态机 + `osDelay(5)`；
- **1s 节拍**：`ms_accumulator += 50`，累到 1000 才执行传感器 tick、数据聚合、仲裁、printf（`main.c:62-141`）。

> **必答细节（评委很爱抓）**：LiteOS-M 默认 tick = 10ms，所以 `osDelay(5)` = **50ms**，不是 5ms——这正是累加器每次加 50 的原因。`AlarmBeeperBeepShort()` 里 `osDelay(10)` 也就约 100ms。

### 2. 中断 + 轮询两条腿（PIR）
`sensor_infrared.c`：`IoTGpioRegisterIsrFunc(..., IOT_GPIO_EDGE_RISE_LEVEL_HIGH, OnInfraredIsr, NULL)` 注册**上升沿中断**，ISR 里把 `g_seconds_since_motion` 清零、计数 +1——保证**快速经过也不会漏**；
`SensorInfraredTick1s()` 每秒自增，`GetRealtime()` 再读一次当前电平，高则刷新缓存、低则清缓存——保证“人还在动”能被看到。
> 这就是“中断管瞬时、轮询管状态”，只用其中一种都会出错。

### 3. 滑动窗口去抖（门磁/按键）
`sensor_door.c`：`g_debounce_history = ((hist << 1) | (val == 1)) & 0x07`，**连续 3 次（3 秒）都是 1 才认开门、连续 3 次 0 才认关门**；
`sensor_sos.c`：8 位移位历史，**全 0（连续 8 次 50ms 都是按下）** 才触发，天然滤掉抖动和误触。
> 加分的说法：机械触点抖动是毫秒到几十毫秒级，用“位历史 + 全 1/全 0 判定”比固定延时更稳，也省一个定时器。

### 4. 优先级仲裁（同一时刻只报最主要的一条）
`main.c:84-116` 的 `if / else if` 链：
**SOS(1) > 高温(2) > 无活动(3) > 门长开(4) > 低温(5) > 正常(0)**。
`g_care_data.current_alert` 只保留“最高优先级的那一条”，避免一次开门同时刷出三条告警。
> 追问“为什么 SOS 最高”：主动按键是老人明确表达求助，其他都是推断，推断永远让位于明确请求。

### 5. 三档声光（本地也要分级）
`alarm_beeper.c` 状态机按 `g_current_level`：
- NORMAL：**2000ms** 周期，LED 亮 100ms（心跳，证明板子活着），蜂鸣器不响；
- WARNING：**1500ms** 周期，LED 双闪 120ms×2，蜂鸣器前两段短鸣；
- CRITICAL：**400ms** 周期，亮/响 200ms 交替（急促啸叫 + 爆闪）。
`AlarmBeeperMute()`（F2 触发）置静音锁，但**新的 CRITICAL 会解锁**——防止“静音后再也听不到”。

## 六、串口遥测协议（这次答对了很加分）

固件每秒打印一行（`main.c:124-137`）：

```json
{"type":"telemetry","uptime":12,"motion":1,"no_motion_sec":0,"door":0,
 "door_sec":0,"temp":24.5,"humi":53.0,"sos":0,"alert":0,"level":0,"count":3}
```

| 字段 | 含义 | 网关映射 |
|---|---|---|
| `motion` | 当前是否检测到活动 | → `pirDetected` |
| `no_motion_sec` | 距上次活动多少秒 | → `lastMotionTs = now - no_motion_sec` |
| `door` / `door_sec` | 门开状态 / 已开时长 | → `doorOpen`（时长由网关按快照连续性自行累计） |
| `temp` / `humi` | 温湿度 | → `temperature` / `humidity` |
| `sos` | 是否处于求助态 | → **额外补一条 SOS 事件（L3）** |
| `alert` / `level` | 告警类型 / 等级枚举 | 参考字段（判定仍以数值为准，不重复判） |
| `uptime` | 运行秒数 | 写进 `fwVersion` 后缀，便于确认板子活着 |

网关侧实现：`gateway/telemetry.py`（新增）负责翻译，`Api.ingest_snapshot` 在入口判断“是不是遥测帧”，是就先转换再走**同一条**校验/入库/判定路径——串口、UDP、HTTP 三个通道规则完全一致。
**已实测**：新增 10 项单元测试，全套 **71 项 OK**（`python -m unittest discover -s tests -q`）。

## 七、20 个必答问题（问法 → 怎么答 → 追问怎么接）

1. **板子上跑的是什么系统？**
   OpenHarmony 轻量系统（LiteOS-M 内核），用 CMSIS-RTOS2 接口（`osThreadNew`/`osDelay`），`SYS_RUN` 宏把应用注册成启动任务。
   ▸ 追问“和标准 Linux 区别”：无 MMU、无进程概念、任务是线程模型，内存几百 KB 级，所以不能用 Python/Java 那套。

2. **为什么只建一个任务？**
   逻辑简单、耦合低：50ms 里做按键+声光，1s 里做采集+判定+上报；多任务反而要处理锁和优先级反转。8KB 栈足够（无递归、无大块局部变量）。

3. **`osDelay(5)` 是 5 毫秒吗？**
   不是，是 5 个 tick；LiteOS-M 默认 tick=10ms，所以是 **50ms**。这也解释了累加器为什么每次 +50。

4. **PIR 用中断还是轮询？**
   两个都用：中断保证不漏瞬时经过；1s 轮询确认“人是否还在活动区”。只用中断会在人静止不动时误判无活动。

5. **门磁怎么判开关？**
   内部上拉 + 干簧管接地：**闭合=0=关门，断开=1=开门**；用 8 位移位历史做 3 次一致性去抖，避免触点抖动导致时长乱跳。

6. **按键误触怎么防？**
   连续 8 次（约 400ms）采样全为 0 才认按下；`!g_sos_state` 保证按住不会连续触发，需 F2 才能清除。

7. **告警怎么分级？**
   代码里 `alert_level_t` 四档（NORMAL/INFO/WARNING/CRITICAL），主循环把 5 类情况按优先级映射成三档实际告警：SOS 与高温判 CRITICAL，无活动判 CRITICAL（等网关细化 L1/L2/L3），门长开与低温判 WARNING。

8. **为什么判定不放在板子上？**
   板子算力/内存有限，且阈值要能远程调、规则要能迭代；放网关改配置即生效。板端保留最小规则 + 声光兜底，断网也能响。

9. **板子和 APP 之间怎么通信？**
   目前走**串口**：板子 115200 打印 JSON → 网关 `--serial COMx` 读取 → 适配 → HTTP 给 APP。原因是比赛现场 WiFi 不可控，串口最稳；协议层与 WiFi 版一致，换传输不改判定。

10. **有没有做 WiFi？**
    软件包里有 WiFi STA + HTTP POST 的完整实现（`software/firmware/net.c`，含断网环形缓存），但这次演示用串口链路。**如实说：WiFi 版未在本次板子上联调。**

11. **温湿度是真传感器读的吗？**
    **不是。** 当前 `sensor_environment.c` 是 16 点波表拟真（24.5±0.5℃、53±1.5%RH），因为 E53_IS1 套件里 SHT30 还没焊/接线；I2C 引脚（GPIO0/1）和读取接口都预留了，接上就是真数据。界面与文档都标注了数据来源。
    ▸ 这是**必须诚实**的一条，评委一问代码就露，主动说反而加分。

12. **为什么阈值定 30 秒？**
    现场演示压缩版（真实场景 2–4 小时）。阈值集中在 `elderly_care_config.h`，一行可改；量产应由 APP 下发、网关统一管理。

13. **无活动会不会误报？**
    会，所以真实系统要有：白天/夜间不同阈值、门开着不判无活动、午睡时段豁免、同类型告警冷却。这些**在网关侧已经实现**（`gateway/rules.py` 的三条融合规则），板端只做兜底。

14. **SOS 按下之后发生什么？**
    板端立刻进 CRITICAL：400ms 急闪 + 连续啸叫；串口帧 `sos=1` → 网关适配层补 SOS 事件 → L3 告警入库 → 电脑声光 + APP 弹窗；家属在 APP 处置后，板端可按 F2 消警。

15. **怎么证明板子在工作？**
    三处：串口每秒一行 JSON 且 `uptime` 递增；LED 2 秒心跳；网关看板显示 `source=hardware` 与设备在线。

16. **内存够吗？会泄漏吗？**
    全局静态变量 + 固定栈 8KB，**没有 malloc/free**（printf 走标准库缓冲），不存在堆碎片与泄漏；代价是不支持动态扩展设备数量。

17. **为什么变量加 volatile？**
    `g_seconds_since_motion` 等在中断里写、主循环里读，不加 `volatile` 编译器可能把它缓存到寄存器，导致计时不更新。

18. **蜂鸣器参数？**
    PWM1，频率 **4000Hz**、占空比 **50%**（无源蜂鸣器需要方波驱动）；关的时候 `IoTPwmStop` 而不是把占空比设 0，避免持续耗电与发热。

19. **这套代码你写了多少？**
    架构（任务划分/状态机/优先级）、引脚与电气判断、去抖方案、阈值与演示口径由我们定；AI 辅助生成了初稿，我们逐行核对并现场调试——可以随时指出 `osDelay` 单位、去抖位数、PWM 参数这些细节。
    ▸ 千万别答“全是我原创手写”或“全是 AI 写的”，按实际分工说。

20. **现在还有什么没做完？**
    三件，都清楚：①温度传感器还是拟真，待接 SHT30；②WiFi/HTTP 版固件已写但未在本次板子联调；③板端语音播报没有（Hi3861 无音频外设，由网关电脑扬声器代播）。

## 十、现场演示顺序（2 分钟版）

1. 串口工具（或 `python scripts\siren.py` 不用）——直接看板子打印：`uptime` 递增、LED 心跳 → 证明活着；
2. 手在 PIR 前挥一下：串口 `motion=1`、`no_motion_sec` 归零；
3. 按 F1：串口 `sos=1` → 板端 400ms 急闪啸叫 → 电脑网关声光 → APP 弹出 L3；
4. 开门磁（或手动短接断开）：`door=1`、`door_sec` 递增，15 秒后 `level` 变 WARNING，声光转 1.5s 双闪；
5. 按 F2：声音停、LED 转心跳 → 证明“本地也能收尾”；
6. 电脑端 `python run_gateway.py --port 8780 --lan --serial COM3 --baud 115200` 打印 `source=hardware`，APP 首页显示“真实采集”。
