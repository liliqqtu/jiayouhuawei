## 二、代码改动

### 2.1 固件（15 个 .c/h，2198 行）

- **新增 `local_rule.c/h`（373 行）**：纯逻辑模块，只吃「时间 + 温湿度 + 门磁开合」，
  不碰 GPIO、不碰 socket（静态检查会验证这一点）。判据、阈值全部来自 `config.h`。
  - 分级：疑似火情（≥55℃ 或 180 秒升 8℃）与求助为 L3 立即项；温度/湿度/门磁为 L1/L2；

  - 只在**等级变化**时补报一次事件，不是每帧都报。
- **`config.h`**：新增本地阈值段（与网关 `Thresholds` 同值）、确认/回差窗口、

# 第二轮补充（当晚）：把"评委能不能自己看到"补上

## 为什么加这三样

复盘演示流程时发现一个短板：**所有效果都依赖 APP**。装 APP 要签名、挑机型、填 IP，
任何一步卡住，评委就只能听我讲。补三样东西，让它"不靠嘴"：

| 新增 | 解决什么 | 谁受益 |
|---|---|---|
| Web 看板 `/` | 浏览器打开就能看状态，手机也行，零安装 | 评委、路演的观众、我们自己排障 |
| 一键演示 `demo.ps1` | 忘了先起哪个、端口被占、IP 写错——三个坑一次填平 | 现场演示、录视频 |
| 压测 `bench.py` | "网关能扛多少设备"从"应该没问题"变成具体数字 | 答辩 Q&A |

## Web 看板（`gateway/dashboard.py` + `server.py` 路由）

- 根路径 `/`（以及 `/dashboard`、`/index.html`）返回 HTML，走 `_send_html`，
  与 JSON 接口完全分离，不影响原有 16 个接口的行为。
- 页面**零外部资源**：没有 CDN、没有字体、没有图片，断网也能渲染——这点是为现场选的。
- 每 3 秒 `fetch` 五个已有接口（snapshot / device / pending / alarms / health），不新增后端接口。
- 内容按"评委一眼要什么"排序：顶部在线状态 → 大标题（一切正常 / 有 n 条待确认 / 设备离线）
  → 六个指标 → 待处理告警（按等级配色）→ 最近告警表 → 接口速查。
- 离线超过 10 秒顶部变黄，写明"数据已过期"，避免看板比 APP 乐观。

## 一键演示（`scripts/demo.ps1`）

- 顺序：查端口占用 → 起 `run_gateway.py --lan --udp-port 9998` → 等 `/health` 通 → 起模拟器循环。
- 子进程用 `Start-Process -RedirectStandardOutput` 起，日志落 `data/demo_*.log`，
  不弹一堆黑窗口；pid 写进 `.demo.json`，`-Stop` 精确定点清理。
- 失败路径明确：端口被占直接告诉你"先 -Stop 或换 -Port"，网关起不来打印 err 日志尾部。

### 晚：演示前实测发现的播报缺陷（已修）

**现象**：L3 警笛用 `winsound` 的 `SND_LOOP` 无限循环时会**独占音频设备**，紧接着的 SAPI 语音播报被卡住（`subprocess` 一直等到 25 秒超时），实测每轮播报间隔被拖到 30 秒以上，听起来像“响一下就没声了”。

**改法**（`gateway/siren_wav.py` + `gateway/server.py`）：

1. L3 音源从“2 秒循环”改成 **6 秒扫频长音**（600→1600Hz 来回 6 遍），每轮 `play_once` 播一次，不占设备；
2. `LEVEL_INTERVAL` 从 `L3=6` 改成 `L3=2`（6 秒鞭炮 + 语音 + 2 秒 → 实测一轮约 10 秒，听觉上接近不间断）；
3. 语音子进程超时 25s→10s，避免再次把播报线程拖死。

**实测**：`19:26:39 / 19:26:49 / 19:26:59 / 19:27:09 / 19:27:18 / 19:27:28` —— 稳定约 10 秒一轮；关闭告警后立刻出现 `[siren] 告警已全部解除，停止提示`，无残留声音。PPT 第 11 页同步改为“约每 10 秒一轮”。

**新增**：`docs/演示走查清单.md`（10 节，含命令、预期现象、9 条故障速查），给现场走查和录屏用。

### 补：demo.ps1 遇到端口占用会自己收拾

用户第一次照清单跑就撞上 `端口 8780 已被占用（pid=22568）`——是上一轮网关没关干净。现在脚本会先看占用者是不是自己的 `run_gateway.py`：是就 `Stop-Process` 后继续启动并提示“已自动停掉”；不是才报错并**打印占用进程的完整命令行**，告诉用户关掉它或换 `-Port`。实测：连跑两次，第二次直接绿色起服务。

### 补二：把"启动"和"报警"分开（用户现场反馈）

用户照清单起服务，结果**一启动就报警**，要求把两者拆开。

**根因**：SirenThread 每轮直接扫 `status=pending` 的告警，库里有上一轮遗留的待确认就立刻播报；
演示时人还没开始讲，电脑先响起来了。

**改法**：

1. `SirenThread` 记下启动时刻 `start_iso`，默认只播 `createdTs >= start_iso` 的告警；

3. `alarm_json` 补 `createdTs` 字段（之前没暴露，判断"是不是启动后的新告警"需要它）。
4. 顺手修了个隐蔽坑：Windows 下 `ThreadingHTTPServer` 带 `allow_reuse_address`，**两个进程能绑同一端口**，

## 补记：重启后“自己报警”的根因与修复（20:20）

### 现象
用户按新方法起 `demo.ps1 -Siren -Voice`，启动 3 秒后仍然播报：
`[siren] 播报 L2：卫生间连续 7 分钟未检测到活动`（EVT-20261027-0010，20:12:17）。

### 根因（两层）
1. `gateway.db` 的 `device` 表保留了上一轮的 `last_motion_ts / door_open_since`。
   网关重启后第一张快照一来，`delta = ts - 旧 last_motion` 已经是 7 分钟，
   规则立刻建单——**断档期间的“静默”其实没有被观察到**。
2. 播报线程的策略是“只响启动之后新产生的告警”，这条恰好是启动后新产生，
   所以被正常播报。前一次修的是“历史待确认不重播”，没修“假告警”。

顺带查出两个更隐蔽的缺陷：
- `prev_door` 从 sqlite 读回来是 `1/0`，而代码写的是 `is True`，
  导致**开→关跳变永远识别不到**（外出抑制失效）、**门磁持续开启永远不报**。
- 设备重启后 `last_motion_ts` 可能为空，但规则只读数据库、不看快照自带字段，
  第一段活动完全判不出来。

### 修复（`gateway/rules.py` + `gateway/config.py`）
- 新增连续性追踪：每个设备记“本次连续观察起点”（第一张实时帧的时间）。
- 时间累积型判定（无活动 / 睡眠超长静默 / 疑似外出 / 门磁持续开启）的起点
  取 `max(设备上报起点, 观察起点)` —— 断档期间的时间不算数。
- 观察起点后 `startup_warmup_sec`（默认 180 秒）内不判这类告警，
  日志打印 `[rules] xxx 首次实时上报，180 秒内不判时间累积型告警`。
- 回放 / 补传帧（快照时间与服务器时间差 > `realtime_tolerance_sec`，默认 120 秒）
  保持原判定 —— `sim/incident.py --type night / door` 这类历史注入照旧立刻出告警。
- `prev_door` 归一化成 bool；`last_motion` 在库里为空时用快照的 `lastMotionTs` 兜底。

### 验证
- 新增 `tests/test_continuity.py`（8 项）：重启旧状态不误报、回放帧照旧报 L3、
  预热过期后恢复、静默起点重算、门磁重算 / 正常报、开→关外出抑制。
- 全套 `Ran 47 tests ... OK`。
- 实测：20:17:43 启动，日志只有预热提示，`/api/v1/alarms/active` = 0 条，无播报；
  随后 `python sim\incident.py --type night` 仍正常生成 L3 NO_MOTION（EVT-0011）。
