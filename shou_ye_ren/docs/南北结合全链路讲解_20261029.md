## 1. 数据是怎么从 GPIO 一路走到手机屏幕的（端到端 12 步）

以“老人在客厅走动”为例，走一遍完整链路：

| 步 | 发生什么 | 代码位置 |
|---|---|---|
| 1 | PIR 检测到热源移动，输出高电平，**上升沿触发硬件中断** | `sensor_infrared.c` `OnInfraredIsr()` |
| 2 | ISR 把静默计时清零、活动计数 +1（`volatile` 变量，ISR 与主循环共享） | 同上 |
| 3 | 主循环 **1 秒** 节拍里把传感器状态聚合进全局结构体 | `elderly_care_main.c` `ElderlyCareTask()` |
| 4 | 主循环按优先级判断：SOS > 高温 > 无活动 > 门长开 > 低温，得出 `alert/level` | 同上 `if/else if` 链 |
| 5 | 声光状态机按等级驱动：正常 2 秒心跳、预警 1.5 秒双闪、紧急 400ms 急闪+啸叫 | `alarm_beeper.c` `AlarmBeeperTick()` |
| 6 | 每秒 `printf` 一行 JSON（`type=telemetry`，12 字段）走串口 115200 | `elderly_care_main.c` |
| 7 | 网关 `SerialIngest` 逐行读串口，`extract_serial_json` 只挑 `{...}` 行 | `gateway/ingest.py` |
| 8 | `telemetry.py` 判定“这是遥测帧”，翻译成**标准 16 字段快照**（`lastMotionTs = now - no_motion_sec` 等） | `gateway/telemetry.py` |
| 9 | `Api.ingest_snapshot()` 统一入口：校验 → 入库（`snapshot` 表自增 id + `UNIQUE(device_id, seq)`） | `gateway/api.py` / `store.py` |
| 10 | `Engine.on_snapshot()`：更新连续性、算沉默时长、按阈值判 L1/L2/L3、去重冷却后建单 | `gateway/rules.py` |
| 11 | 有新单 → `SirenThread` 排进播报队列（警笛 WAV + 中文语音）；Web 看板轮询到新状态 | `gateway/server.py` / `dashboard.py` |
| 12 | APP 每 3 秒 `GET /api/v1/snapshot` + `/api/v1/alarms`，HomeTab/AlarmTab 更新；来源标“真实采集” | `app/.../service/ApiClient.ets` |

**讲这一节的关键**：任何一次演示，都能指着这条链说“数据在哪个文件、哪个函数被处理”，而不是“大概是这样”。

## 2. 南向：Hi3861 固件（为什么有两套）

仓库里有两套固件，**两套都真实存在，且用途不同**，这点必须讲清楚：

| | 队友版 `elderly_care_system` | 我们版 `shou_ye_ren/firmware` |
|---|---|---|
| 行数 | 704 行 C + 5 个 .h | 2198 行 C/H（15 个文件） |
| 定位 | **最小可用**：传感器 → 声光 → 串口 JSON | **完整**：WiFi/HTTP、SNTP、本地阈值兜底、断网缓存 |
| 上报 | 串口打印 JSON（`printf`） | WiFi STA + HTTP POST / UDP；失败进环形缓存 |
| 判定 | 主循环 if/else 五档仲裁 | `local_rule.c` 单指标+时间窗状态机（12 类事件，与网关同名） |
| 时间 | 靠 `uptime` 秒数 | SNTP 校时 → ISO8601 |
| 状态 | 已能在板子上跑（今天演示用这套） | 编过静态检查，**未在本次板子联调** |

### 2.1 队友版结构（现场演示这套）

```
elderly_care_main.c   165 行  任务创建、50ms/1s 双周期、优先级仲裁、遥测 printf
sensor_infrared.c      82 行  PIR：上升沿中断 + 1s tick 计时
sensor_door.c          59 行  干簧管：8 位历史滑动去抖（连续 3 次一致）
emergency_sos.c        78 行  F1 求助 / F2 消警：连续 8 次全 0 才触发
sensor_environment.c   68 行  温湿度：16 点波表拟真（SHT30 未接）
alarm_beeper.c        136 行  蜂鸣器 PWM 4kHz/50% + LED 三档节奏状态机
elderly_care_config.h 116 行  引脚、阈值、枚举、数据结构
```

**四个必须讲清的机制：**

1. **任务模型**：`SYS_RUN(ElderlyCareAppEntry)` 是 OpenHarmony 启动入口宏；`osThreadNew(..., 8KB 栈, osPriorityNormal)` 建任务；`while(1)` 里 50ms 节拍处理按键与声光、1s 节拍做采集/仲裁/上报。
   ▸ 细节：LiteOS-M 默认 tick = 10ms，`osDelay(5)` = **50ms**，所以 1 秒累加器每次 `+= 50`。

2. **PIR 两条腿**：中断（`IOT_GPIO_EDGE_RISE_LEVEL_HIGH`）保证“快速经过不漏”，1 秒轮询保证“人在动能被持续看到”。只用一种都会错。

3. **去抖**：门磁 8 位历史（`hist = ((hist<<1)|val) & 0x07`）连续 3 次一致才认开关；SOS 键连续 8 次（约 400ms）全 0 才触发，且 `!sos_state` 防重复。

4. **优先级仲裁**：SOS(1) > 高温(2) > 无活动(3) > 门长开(4) > 低温(5) > 正常(0)，同一时刻只保留最高一条，避免刷屏。

### 2.2 我们版固件的分层（讲“工程化”时用）

```
app_main.c   522 行  SensorTask（只采样，不碰网络）/ UploadTask（只发包）双任务
drv.c        166 行  GPIO 输入输出：按键、门磁（含上拉与消抖）
env.c        127 行  I2C：SHT30(0x44) + BH1750(0x23) 读取，失败返回 NULL 不编数
local_rule.c 373 行  本地阈值判定状态机（12 类事件、确认/清除双窗口、L3 立即）
biz.c        141 行  业务状态：ACTIVE / ACKNOWLEDGED / CLOSED（板端只认这三种）
net.c        312 行  WiFi STA 连接、HTTP POST、断网环形缓存（16 帧）
sntp.c       122 行  SNTP 校时（无 RTC，依赖网络）
log.h         35 行  LOGI/LOGW/LOGE + `#JSON#` 标记（串口与日志可分辨）
```

**为什么要本地判定**：断网时网关收不到数据，板子必须能自己响。`local_rule.c` 用“单指标 + 时间窗 + 确认窗口”做快反（例如温度 >55℃ 立即 L3，>35℃ 持续 30 秒确认），真正建单仍以网关为准（冷却去重），避免板端反复报十几条。

## 3. 传输层：三个通道如何汇合

```
串口 ─┐
UDP  ─┼→ ingest.py ─→ parse_payload / extract_serial_json
HTTP ─┘                     ↓
                     telemetry.looks_like_telemetry()？
                       是 → telemetry.to_snapshot()（12 字段 → 16 字段）
                       否 → 直接当标准快照
                            ↓
                   Api.ingest_snapshot(body, channel)   ← 唯一入口
```

**为什么这样设计**：
- 三条通道规则完全一致（同一校验、同一入库、同一判定），不会出现“UDP 进来的能报警、串口进来的不报警”；
- `channel` 只用于日志与排障（`http` / `udp` / `serial`）；
- 现场 WiFi 不可控时用串口，实验室用 HTTP，两者都通。

**协议适配的关键映射**（`telemetry.py`）：

| 板端字段 | 标准快照字段 | 换算 |
|---|---|---|
| `motion` | `pirDetected` | 直接 |
| `no_motion_sec` | `lastMotionTs` | `now - no_motion_sec` |
| `door` / `door_sec` | `doorOpen` | 直接（时长由网关按连续性自行累计） |
| `temp` / `humi` | `temperature` / `humidity` | 直接，缺失为 `null` |
| `sos` | 额外补一条 **SOS 事件** | 由 `to_sos_event()` 生成，走 `DIRECT_EVENT_TYPES` |
| `uptime` | 写进 `fwVersion` 后缀 | 便于确认设备活着 |

### 4.2 五个接口（答辩最常被问的）

| 方法 | 路径 | 作用 | 要点 |
|---|---|---|---|
| POST | `/api/v1/snapshot` | 上报一帧 | 幂等：同设备同 seq 2 分钟内视为重试 |
| POST | `/api/v1/events` | 上报告警事件 | SOS/GAS/SMOKE 直接建单 |
| GET | `/api/v1/alarms?status=&deviceId=` | 查告警 | 状态 + 设备双过滤 |

### 4.3 数据库 5 张表

| 表 | 关键字段 | 说明 |
|---|---|---|
| `snapshot` | `id`(自增 PK)、`device_id`、`seq`、`ts`、`created_at`、16 字段 JSON | 加 `UNIQUE(device_id, seq)` 防重启覆盖 |
| `alarm` | `event_id`(EVT-YYYYMMDD-####)、`type`、`level`、`status`、`ts`、`created_at`、`updated_at`、`evidence` | 状态机 ACTIVE→ACKED→CLOSED |
| `activity` | `device_id`、`ts`、`count` | 每 2 小时聚合柱状图数据源 |
| `device` | `device_id`、`source`、`fw_version`、`last_seen` | 谁上报谁建档 |
| `kv` | `key`、`value` | 阈值、告警序号、家庭组等 |

索引：`idx_snapshot_ts`、`idx_alarm_status`、`idx_alarm_type`、`idx_activity_ts`。

### 4.4 声光播报（一条独立线程）

- L3：6 秒扫频警笛（600→1600Hz）`play_once` 循环 + 中文语音“紧急求助，请立即处理”，间隔约 7 秒；
- L2：1.5 秒三声 + 语音，间隔约 6.5 秒；
- L1：0.8 秒两声 + 语音，间隔约 10 秒；
- 多条待处理按 L3 > L2 > L1 排序轮转；确认后立即停；`--siren` / `--voice` 可分别开关（演示时避免吵到其他组）。
- 语音优先用 Windows `System.Speech` 离线合成，失败退回 `winsound` 蜂鸣。

## 5. 数据契约

### 5.1 快照 16 字段（`SensorSnapshot`）

```json
{
  "deviceId": "bearpi-001", "seq": 128, "ts": "2026-10-29T20:15:03+08:00",
  "pirDetected": true, "lastMotionTs": "2026-10-29T20:15:01+08:00",
  "temperature": 24.5, "humidity": 53.0, "lux": 180,
  "doorOpen": false, "battery": 88, "powerSource": "mains",
  "online": true, "fwVersion": "sim-1.0", "source": "test",
  "rssi": -52, "uptimeSec": 3600
}
```

规则：**未知一律 `null`，不编造**；`source ∈ {hardware, test}`（`real` 归一化为 `hardware`，其余含 `key_sim` 归 `test`）。

### 5.2 事件 15 字段（`AlarmEvent`）+ 10 种类型

`SOS / NO_MOTION / DOOR_OPEN / TEMP_HIGH / TEMP_LOW / HUM_HIGH / HUM_LOW / TEMP_FIRE / LUX_NIGHT_HIGH / LUX_DAY_LOW`
（另有板端上报类型 `TEMP_WARM / TEMP_RISE / HUM_WARN_HIGH / HUM_WARN_LOW`，在 `BOARD_EVENT_TYPES` 里。）

状态机：`ACTIVE →(ack) ACKNOWLEDGED →(close) CLOSED`；`ACTIVE` 超过 `escalate_min`（10 分钟）自动升级并打标。

## 6. 判定引擎：三档 + 融合规则

### 6.1 阈值（`config.py` `Thresholds`，全部可远程改）

| 类别 | 参数 | 默认值 | 说明 |
|---|---|---|---|
| 无活动 | `no_motion_min` | 5 分 | 白天 |
| | `night_no_motion_min` | 3 分 | 夜间（22:00–06:00） |
| | `night_bathroom_min` | 2 分 | 夜间卫生间（最高风险组合） |
| | `sleep_gap_min` | 360 分 | 睡眠期（23:00–07:00）超长静默才算异常 |
| 门 | `door_open_max_min` | 10 分 | 长开提醒 |
| 外出 | `away_max_min` | 120 分 | 疑似外出容忍 |
| 温度 | `temp_warm/high/fire` | 28 / 35 / 55 ℃ | 三级递进 |
| | `temp_rise_delta` / `window` | 8 ℃ / 180 秒 | 短时升温判疑似火情 |
| | `temp_low` | 16 ℃ | |
| 湿度 | `hum_high/warn/low` | 80 / 70 / 25 % | |
| 光照 | `lux_night_high` / `lux_day_low` | 200 lux / 20 lux | 夜间强光 / 白天采光不足 |
| 时间窗 | `startup_warmup_sec` | 180 秒 | 重启后时间累积型告警的预热 |
| | `realtime_tolerance_sec` | 120 秒 | 判定“实时帧”的容差 |
| 午睡 | `nap_enabled/start/end` | 1 / 13 / 15 | 午睡不判无活动 |

### 6.2 三档映射（谁判成什么）

| 等级 | 触发 | 处置要求 |
|---|---|---|
| **L3 紧急** | SOS 求助；`TEMP_FIRE`（≥55℃ 或 180 秒内 +8℃）；夜间卫生间无活动 | 立即电话/上门 |
| **L2 关注** | 白天 5 分钟无活动；湿度越界（80%/25%）；睡眠期超长静默；待确认超时升级 | 尽快确认 |
| **L1 提醒** | 温湿度轻微越界（28/16℃、70/35%）；门长开；夜间异常强光；白天采光不足 | 方便时处理 |

### 6.3 三条融合规则（这是“为什么不误报”的核心）

1. **外出抑制**：`doorOpen == true` 且持续时间未超阈值 → 不判“无活动”（人可能刚出门/在门口）。
2. **夜间加权**：`is_night(22..6)` 时阈值降档（5→3 分钟），卫生间再降到 2 分钟；睡眠时段（23..7）改用 `sleep_gap_min`（360 分钟）。
3. **冷却去重**：同 `(type, deviceId)` 在冷却窗口内不重复建单；跨设备互不影响（`active_alarm(type, device_id)` 按设备查）。

### 6.4 三个容易漏的工程细节（讲出来很加分）

- **连续性追踪**：网关刚启动/断档后的 180 秒内，只让“瞬时类”告警（温度、门磁、求助）通过；时间累积类（无活动）必须**亲眼观察满阈值**才判——否则重启就会拿一帧“沉默 7 分钟”的旧数据误报（这是我们真踩过的坑）。
- **回放帧豁免**：设备补传的历史帧（`ts` 与服务器时间差 > 120 秒）不参与实时判定，只入库。
- **事件编号**：`EVT-YYYYMMDD-####` 由 `kv` 计数器 + 当日最大序号取大值决定，**不能用 `COUNT(*)+1`**（删过记录后会撞唯一键）。

## 8. 一次 SOS 的完整生命周期

```
老人长按（板 F1 或 APP 按钮）
   │
   ├─ 板端：紧急态 → 400ms 急闪 + 连续啸叫；串口 printf {"sos":1}
   │        └─ 网关 telemetry.to_sos_event() → 建 L3 单
   │
   └─ APP：POST /api/v1/events {type:SOS}
            └─ 网关 rules.on_event() → 直接建单（DIRECT_EVENT_TYPES）
   │
   ▼
告警入库：status=ACTIVE，event_id=EVT-20261029-0007，evidence 存触发证据
   │
   ├─ 网关：SirenThread 立即切 L3 播报（警笛 + “紧急求助，请立即处理”）
   ├─ Web 看板：红色横幅“有 1 条待确认告警”
   └─ APP：3 秒内拉到 → 告警页红卡 + 新角标 + 本机震动提示 + TTS 播报
   │
家属操作：填处置结果（必填 ≤200 字）→ 确认 → 关闭
   │
   ├─ APP：POST /alarms/{id}/ack  → status=ACKNOWLEDGED
   ├─ APP：POST /alarms/{id}/close → status=CLOSED，记录处置人与时间线
   └─ 网关：下一轮播报跳过已确认；看板计数减一
   │
老人端（板子）：从 /alarms/active 拉取到“已确认”→ LED 转常亮、停止啸叫
```

> 断网时：APP 的 `Outbox` 先入队（Preferences），网关恢复后 9 秒一轮补发，补发成功即从队列移除；板子不依赖这个闭环，仍会本地继续响，直到有人按 F2。

## 9. 可靠性与异常处理

| 场景 | 处理 | 代码 |
|---|---|---|
| 设备重启后 seq 从 0 开始 | 自增 id 主键 + `UNIQUE(device_id,seq)`；2 分钟内同 seq 视为重试，超时自动重编号 | `store.save_snapshot` |
| 设备时钟跑到未来 | 超过服务器 300 秒才纠偏，并打 `timeAdjusted` 标记 | `api.ingest_snapshot` |
| 设备补传历史数据 | `BACKFILL_WINDOW_SECONDS=300` 外的帧只入库不判 | `rules.on_snapshot` |
| 网关重启 | 180 秒预热，时间累积型告警需重新观察 | `rules._silence` |
| 网关离线 | APP 显示“离线 · 数据已过期”，保留最后一次数据并标注时间 | HomeTab |
| APP 处置时网关掉线 | 入 `Outbox`，恢复后自动补发，界面显示待补发条数 | `Outbox.ets` |
| 端口被占 | 启动前检测，提示 `pid` 或换端口 | `server.port_busy` |
| 拨号不可用 | 三级降级（dial → tel: → 弹窗复制号码） | `CallUtils.ets` |
| 相册权限被拒 | 退回系统“保存到相册”选择器，不阻塞流程 | `ReportExporter.ets` |

## 10. 十个关键技术决策与取舍

1. **判定放网关不放板子**：板算力小、阈值要能远程调、规则要能迭代；板端只留兜底。
2. **三通道共用 `ingest_snapshot`**：避免“哪个入口进来的”导致行为不一致。
3. **板端只上报“事实”（信号/时长），不报“结论”**：`no_motion_sec` 而不是“老人摔倒了”，从协议层就杜绝过度推断。
4. **告警状态机只有三态**：ACTIVE/ACKNOWLEDGED/CLOSED，板端也只认三态，跨端一致。
5. **SQLite + WAL**：单机零依赖、断电可恢复、查询够快（演示规模 10 万帧无压力）。
6. **Web 看板零外部资源**：现场没网也能开，评委席直接看。
7. **APP 用 3 秒轮询而不是推送**：局域网、无云、无公网；代价是退出后台不提醒（已如实写入局限）。
8. **离线队列**：处置动作比读数更重要，宁可排队也不能丢。
9. **来源标记贯穿全链路**：`source` 从板子到界面，任何模拟数据都显式标注。
10. **用词合规做成脚本**：`check_words.py` 进构建前检查，避免把“无活动”写成体态医学结论类词汇（词表见脚本 `FORBIDDEN`）。

## 12. 三版讲解稿

### 12.1 三分钟（电梯版）

> 这是一套独居老人居家安全系统。屋里放一块 BearPi 开发板，接人体红外、门磁、求助按钮。
> 板子每秒钟把“有没有活动、多久没动、门开没开、温湿度多少”通过串口发一行 JSON 给家里的网关。
> 网关做三件事：判等级、留记录、报警。判等级分三档：求助和夜间卫生间长时间没动静是紧急，白天持续没活动是关注，温湿度越界和门长时间没关是提醒。
> 报警不只弹手机——屋里会响、会播报中文，老人自己也听得见。
> 手机上能看五项指标、处置告警、看七日报告；家属可以组家庭组一起看。
> 我们的边界很清楚：只判断有没有活动，不做体态识别，不装摄像头，数据不出家门。

### 12.2 八分钟（结构版）

1. 问题与定位（1 分钟）：独居老人“出事了没人知道”，三个断点：不知道、来不及、说不清。
2. 架构（1.5 分钟）：南向感知 → 串口 → 网关判定 → APP 处置；分层理由。
3. 判定引擎（2 分钟）：三档阈值 + 外出抑制/夜间加权/冷却去重 + 180 秒预热。
4. 端到端演示（2 分钟）：串口数据 → 按 F1 → 网关响 → APP 告警 → 填处置关闭。
5. 工程性证据（1 分钟）：71 项测试、来源标记、用词合规脚本、离线补发。
6. 局限与下一步（0.5 分钟）：温湿度拟真、WiFi 未联调、无推送。

### 12.3 二十分钟（代码版）

按本文第 1→9 节顺序讲，每节配一个“点开这个文件给你看”的动作：
`elderly_care_main.c`（仲裁）→ `sensor_door.c`（去抖）→ `ingest.py`（三通道）→ `telemetry.py`（协议适配）→ `rules.py`（判定）→ `store.py`（幂等与编号）→ `server.py`（播报线程）→ `ApiClient.ets`（超时与错误归一）→ `AlarmTab.ets`（处置闭环）→ `Outbox.ets`（离线补发）。
