# 四、必须能讲出来的 10 个原理（每条先背“一句话”，再准备“展开三句”）

### 1. 系统分层
**一句话**：南向板子只负责“采+报+本地兜底”，判定和理解全在网关，北向 APP 只负责“看+处置”。
**展开**：板子算力有限（Hi3861 无 MMU、内存百 KB 级），把规则放网关，改阈值不用重新烧板；APP 只轮询，不参与判定，保证结论唯一。

### 2. 数据契约
**一句话**：一条快照 16 个字段、一条告警 15 个字段，字段名和语义在 `docs/hardware-contract.md` 冻结，三端都按它写。
**展开**：没接的传感器写 `null` 不写 0（0 会被误判成“温度 0 度”）；`source` 只有 `hardware`/`test` 两种，界面据此标注来源。

### 3. 三档分级
**一句话**：L1 提醒（环境越界）、L2 关注（持续无活动）、L3 紧急（求助/夜间卫生间/疑似火情）。
**展开**：分级决定播报节奏（L1 两声轻提示/15s、L2 三声中速/10s、L3 连续警笛/6s 长音）和 APP 颜色；**同一条告警可升级**（L1→L2→L3，按 `created_at` 计时，不看设备时间，避免历史数据一上来就“已升级”）。

### 4. 三条融合规则（最容易被追问，必须背）
**一句话**：外出抑制、夜间加权、冷却去重。
- **外出抑制**：门开着且刚有活动 → 人在家走动，此时“无活动”不成立；门磁持续开启超时反而报 L1（防忘关门）；门从开到关且随后有 PIR → 判“已回家”而不是“外出未归”。
- **夜间加权**：白天无活动 5 分钟才 L2；夜间卫生间 2 分钟就 L3（起夜停留时间长是危险信号）。
- **冷却去重**：同设备同类型告警在冷却期内只报一次，避免刷屏；不同类型/不同设备互不影响。

### 5. 启动预热与连续性（工程细节，加分项）
**一句话**：网关重启后 180 秒内不判“无活动/门未关”这类**累积型**告警。
**展开**：重启瞬间拿到的历史时间戳会让“沉默 7 分钟”瞬间成立 → 假告警；连续观察满阈值才判；瞬时类（SOS/温度/门磁已开）不受限。

### 6. 断网续传
**一句话**：板子有 16 帧环形缓存，断网先存、恢复后按 `seq` 顺序补发；网关用 `UNIQUE(device_id, seq)` 去重。
**展开**：`seq` 单调递增且重启不归零；2 分钟内重复视为重试丢弃，超时自动重编号，保证不丢也不重。

### 7. 下行确认闭环（南向特色）
**一句话**：APP 确认后，板子 10 秒内轮询 `/api/v1/alarms/active` 得知“已处理”，停响、转灯。
**展开**：没有这条，板子会一直响到断电——这正是我们“闭环”比只上报多走的一步。

### 8. 本地兜底
**一句话**：网关挂掉时，板子用 `local_rule.c` 自己按阈值判 L1/L2/L3，靠 LED/蜂鸣器提醒。
**展开**：阈值与网关同值（`config.h` 与 `config.py` 都有，`scripts/check_firmware.py` 会校验一致性）；L3 立即响，L1/L2 需连续满足 30 秒防抖。

### 9. 数据诚信
**一句话**：模拟数据 `source=test`，APP 显式标“测试/模拟”，首页黄字提示；没有的传感器显示 `—`，绝不编造。
**展开**：这是赛题之外的“工程伦理”分；评委最爱问“这是真的吗”，答“界面上标了来源，你可以现场看”最有力。

### 10. 测试与可复现
**一句话**：网关 61 项单元测试、固件静态自检、禁词扫描，`python -m unittest discover -s tests -q` 一条命令可复现。
**展开**：测试覆盖判定三档、去重、跨设备、重启不覆盖、时间纠偏、设备建档、事件号防冲突等；固件本机无源码树**未编译上板**（如实说）。

# 五、快问快答（被问到的原话怎么回）

**Q1：这作品是 AI 写的吗？**
结构、判定规则、阈值、调试是我们自己定的；AI 用在代码提示、文档润色、部分 UI 素材。核心是 `gateway/rules.py` 的判定和 `firmware/local_rule.c` 的兜底——这两块我可以现场逐行讲。

**Q2：你们的创新点是什么？**
三个：①**三档分级播报**（不是所有告警一个响法，L1 轻提示、L3 连续警笛）；②**睡眠期抑制**（23:00–07:00 只对卫生间/求助升级，避免夜里瞎响吓到老人）；③**本地兜底 + 下行确认闭环**（网关挂了板子自己判，APP 确认后板子会停），这两条是“不止报警，还能收尾”。

**Q3：为什么判定放网关不放板子？**
板子算力/内存有限，且阈值需要能远程调、判定规则要能迭代；放网关改一行配置就生效，不用重新烧录。板子只保留兜底的最小规则。

**Q4：怎么防误报？**
四条：门开不判无活动、夜间/白天不同阈值、同类型告警冷却去重、启动后 180 秒预热；另外温度有“8 分钟升 8℃”的趋势判定而不是单点阈值。

**Q5：老人洗澡/午睡会不会误报？**
午睡时段（13:00–15:00）不判无活动（可在 APP「个性化设置」里开关）；洗澡属于卫生间短时停留，夜间阈值 2 分钟只对“长时间无活动”触发，不是一进去就报。

**Q6：没有摄像头，怎么知道老人出事了？**
我们不判断“在做什么”，只判断“有没有活动、多久没活动”。这是刻意的隐私设计：无摄像头、无麦克风、不上传视频，符合居家场景的接受度。

**Q7：数据会上传云端吗？**
不上传。网关是本地 Python 服务 + SQLite，APP 只在局域网轮询；家庭组数据也存在网关内存里。代价是没有远程推送（见 Q12）。

**Q8：为什么没有系统推送/短信？**
需要华为账号、Push Kit、云端服务器和备案，超出赛题“居家本地”的范围；我们的替代是：网关声光播报（家里能听见）+ APP 前台提醒（手机在看时震动能响）+ 家庭组多人同时看。

**Q9：三个人同时看，会不会看到不同数据？**
不会。家庭组是同一个网关、同一份数据，APP 只是不同终端轮询同一接口；切换设备是全局的，首页/告警/报告会一起刷新。

**Q10：怎么保证数据不丢？**
板子环形缓存 16 帧 + 递增 `seq`；网关 `UNIQUE(device_id, seq)` 去重、重启后自增主键不覆盖历史；实测拔网 1 分钟恢复后 `seq` 连续、看板无跳变。

**Q11：固件编译过吗？上过板吗？**
源码完整（8 个文件、含 `BUILD.gn`），但**本机没有 Hi3861 源码树，未编译上板**，由硬件组完成；我们做了静态自检（`scripts/check_firmware.py`）与契约校验。这条不掩饰。

**Q12：板子上的语音播报怎么做的？**
板子（Hi3861）没有音频外设，播报由**网关电脑的扬声器**代播（`--voice`），板端只有 LED + 可选蜂鸣器。这是硬件限制下的取舍，如实说明。

**Q13：数据是模拟的还是真的？**
现在演示是模拟数据，界面显式标注“测试/模拟”；真实采集接上板子后来源会变成“真实采集”。两者在数据库里用 `source` 区分，可查。

**Q14：为什么用 Python 写网关？**
零第三方依赖、`python run_gateway.py` 就能跑，评委能一条命令复现；并发用 `ThreadingHTTPServer` + SQLite WAL 足够支撑 1Hz 上报。

**Q15：SQLite 会不会写坏？**
用 WAL 模式、单连接串行写、事务提交；写入失败会重试并记日志，测试里覆盖了重启不覆盖历史与并发 seq 冲突。

**Q16：阈值怎么定？为什么是 5 分钟、35℃？**
来自“老人居家常识 + 可调”的思路：35℃ 是室内高温不适的常见界线、80% 湿度易霉、5 分钟无活动是白天保守值（夜间卫生间收紧到 2 分钟）；全部可在 APP 个性化设置里改，改完立即生效并持久化。

**Q17：如果老人把设备拔了/断电呢？**
10 秒收不到新数据判“设备离线”，APP 显示“数据已过期，以下是最后一次上报”，不拿旧数据当现状；恢复后自动续上。

**Q18：你们做了几端？规模多大？**
三端：南向固件（Hi3861，约 1100 行 C）、网关（Python，约 2000 行）、北向 APP（ArkTS，约 6000 行）；61 项网关单测，APP 在模拟器全流程实测。

**Q19：赛题第 X 条要求你们实现了吗？**（对着第三节那张表答）
逐条对，缺的（如燃气/烟感）是**没有对应传感器**，接口和判定已留好，硬件到位即可接入，不夸大。

**Q20：AI 生成的代码占多少？**
按官方口径回答：AI 用于提示与润色，架构、判定规则、调试、验证由团队完成；核心逻辑能讲、能改、能查——这三点随时可以现场演示。

# 七、临场 3 句保底话术

- 被问到没做的：**“这条我们没做，原因是 X；如果要补，我会从 Y 开始做。”**——比硬编强十倍。
- 被问到细节答不上：**“具体数值我记不准，代码里有，我可以现在打开给你看。”**
- 被质疑真实度：**“界面上标了数据来源，模拟数据会显示测试/模拟，您可以现场点一下。”**
